Services

Four things, usually combined. Most engagements start with one deliverable and grow into the toolchain around it, because the writing and the pipeline are the same problem.

01

Technical writing

Documentation written from the source: reading the code, running the product, and interviewing the engineers who built it. Drafts arrive as pull requests in your repository, so your team reviews them the way they review everything else.

  • API and CLI reference material
  • Installation, configuration and upgrade guides
  • Tutorials and getting-started paths
  • Release notes and changelogs
  • Internal engineering handbooks and runbooks

02

Documentation sites

Static documentation sites that load fast, search well and cost almost nothing to run. Content lives in AsciiDoc or Markdown in Git; the site is a build artefact, not a database.

  • Antora for multi-repo, multi-version documentation
  • Docusaurus or a comparable generator for lighter sites
  • Theming to match your product and brand
  • Client-side or hosted search
  • Versioned URLs and redirect maps

03

Docs-as-code pipelines

The build that makes documentation part of the release rather than a task after it. Every pull request builds the site, checks the prose and posts a preview link; every release publishes a version.

  • GitHub Actions, GitLab CI or Jenkins
  • Broken-link and build-failure gates
  • Vale style checks and a house style guide
  • Preview deployments for reviewers
  • Versioned publishing tied to release tags

04

Migration and audit

Moving documentation out of a wiki and into the repository, or working out what is wrong with what you have before spending anything on writing.

  • Confluence, Word or legacy wiki to AsciiDoc or Markdown
  • Content inventory, deduplication and cull
  • Redirects so existing links keep working
  • A one-week audit with a prioritised plan
  • Information architecture for what comes next

Questions

How long does a project take?

An audit is a week. A single guide or reference set is usually two to four weeks. A full site with a pipeline behind it runs six to ten weeks, depending on how much content already exists and how available your engineers are.

Do you work in our repo and review process?

Yes, that is the default. I take a branch, open pull requests, and respond to review comments. If your docs live somewhere else, moving them into the repo is usually the first thing we discuss.

What time zones do you cover?

I work remotely with clients worldwide and arrange a fixed overlap window with your team. Most of the work is asynchronous, in writing, which is what makes distance workable.

Can you work with our existing toolchain?

Usually. Antora, Docusaurus, Hugo, MkDocs, Sphinx and plain Markdown in a static host are all familiar territory. I would rather improve what you run than replace it, unless replacing it is genuinely cheaper.

Do you sign NDAs?

Yes. Most of the work involves unreleased product and internal systems, so an NDA before the first technical conversation is normal.

What if we have no docs at all?

That is often the easier starting point. We agree what the first release of the documentation must cover, build the smallest site that carries it, and grow from there rather than trying to document everything at once.

Can you train our engineers to write?

Yes: a style guide they can actually follow, templates for the common page types, review checklists, and a working session or two. The aim is that routine updates stop needing me.

How do you handle versioning and releases?

Documentation branches follow product versions, and the site publishes each supported version at its own URL with a version switcher. Release notes are drafted during the cycle, not written the night before.

Something here fit your problem?

Send a short description of the product and the state of the docs today. A reply with scope and a rough timeline usually follows within two working days.
